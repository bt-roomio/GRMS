## 1. Старт и карта экранов

Что нужно, чтобы сделать первый запрос, и какие экраны предстоит собрать.

### 1.1. С чего начать

**Базовый URL** — `https://<api-host>/api/v1/`. Аварии живут под `alarms/`, правила — внутри
под `alarms/rules/`, настройки уведомлений — в `main/notification-settings/`.

**Токен.** Логин — обычный JWT-эндпоинт проекта:

```http
POST /api/v1/users/access-token/
Content-Type: application/json

{"email": "engineer@hotel.uz", "password": "..."}
```

```json
{ "access": "eyJhbGciOiJIUzI1NiIs...", "refresh": "eyJhbGciOiJIUzI1NiIs..." }
```

Обновление — `POST /api/v1/users/refresh-token/` с `{"refresh": "..."}`. В полезной нагрузке
access-токена лежат `user_id`, `email`, `tenant_id`, `is_superuser`, `tenant_group_admin` — прав
там **нет**, см. [2.6](#26-права-и-видимость-элементов).

**Первый запрос** — активные аварии:

```bash
curl -s "https://<api-host>/api/v1/alarms/?status=ACTIVE&size=20" \
  -H "Authorization: Bearer $ACCESS"
```

**Swagger** — `/api/v1/swagger/`, ReDoc — `/api/v1/redoc/`. Теги `Alarms` и `Main, Device Profile`.
Схема в JSON — `/api/v1/swagger.json`.

### 1.2. Какие экраны нужны

| Экран / элемент                             | Что показывает                                                                    | Эндпоинты и стримы                                                                                                 |
| ------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Аварии** — таблица с фильтрами            | Активные аварии и журнал закрытых (это один список, отличается фильтром `status`) | `GET alarms/`, WS-стрим `alarms`, `GET alarms/types/` для выпадающего списка типов                                 |
| **Карточка аварии**                         | Детали, история комментариев, кнопки действий                                     | `GET alarms/<id>/`, `GET/POST alarms/<id>/comments/`, `POST alarms/<id>/{ack,clear,assign}/`                       |
| **Массовые действия** в таблице             | Квитировать/закрыть выделенное                                                    | `POST alarms/bulk/ack/`, `POST alarms/bulk/clear/`                                                                 |
| **Плашки на дашборде**                      | Сколько активных, сколько неквитированных, разбивка по severity и типам           | `GET alarms/summary/`                                                                                              |
| **Вкладка «Аварии» в карточке устройства**  | Аварии устройства, включая аварию его шлюза                                       | `GET alarms/?device=<id>`                                                                                          |
| **Вкладка «Аварии» в карточке номера**      | Аварии устройств номера                                                           | `GET alarms/?room=<id>`                                                                                            |
| **Конструктор правил** | Редактор правил: условия, пороги, расписания | `GET/POST alarms/rules/`, `GET/PUT/DELETE alarms/rules/<id>/`, `POST alarms/rules/bulk/`, `POST alarms/rules/preview/`, `GET alarms/rule-templates/`, `GET alarms/available-keys/` |
| **Настройки → Уведомления**                 | Telegram тенанта                                                                  | `GET/PUT main/notification-settings/`                                                                              |
| **Тумблер в карточке устройства**           | «Уведомлять о потере связи»                                                       | поле `notify_on_offline` в `GET/PUT main/device/<id>/`                                                             |

Минимальный объём, который уже полезен: таблица аварий + карточка + `ack`/`clear`. Конструктор
правил можно делать второй итерацией — до него правила заводят через Swagger.

## 2. Общие правила API и права

### 2.1. Заголовки

```http
Authorization: Bearer <access>
Content-Type: application/json
```

### 2.2. Пагинация

Все списки, кроме комментариев, постраничные:

| Параметр | Значение                                |
| -------- | --------------------------------------- |
| `page`   | Номер страницы, с `1`. По умолчанию `1` |
| `size`   | Размер страницы, по умолчанию `15`      |

Ответ:

```jsonc
{ "count": 137, "results": [/* ... */] }
```

`count` — общее число записей под фильтром, ссылок `next`/`previous` нет: считайте число страниц
как `Math.ceil(count / size)`.

### 2.3. Списочные параметры

Повторяются, а не склеиваются через запятую:

```text
?severity=CRITICAL&severity=MAJOR&alarm_type=Device%20Offline&sort_by=-start_ts
```

`URLSearchParams` с `append()` делает это сам:

```ts
const query = new URLSearchParams();
query.set("status", "ACTIVE");
["CRITICAL", "MAJOR"].forEach((s) => query.append("severity", s));
```

### 2.4. Даты

- В ответах — ISO 8601 в **UTC**: `"2026-09-14T10:18:00.412305Z"`. Микросекунды есть, `new Date()`
  их переварит.
- В фильтрах принимается ISO 8601 с зоной: `2026-09-14T00:00:00+05:00`. В query-строке `+`
  обязательно кодировать как `%2B`, иначе он станет пробелом и запрос упадёт с `400`.
  `URLSearchParams` кодирует правильно, ручная склейка строк — нет.
- Поле `created_at` — **Unix-время в миллисекундах** (число), а не строка. Это общая особенность
  проекта: `start_ts`/`end_ts`/`ack_ts`/`clear_ts` — строки ISO, `created_at` — число.
- Время показывайте в часовом поясе отеля. Он лежит в настройках тенанта
  (`additional_info.general_settings.timezone`) целым числом часов — то же смещение использует
  сервер в Telegram-уведомлениях.

### 2.5. Коды ответов

| Код   | Когда                                 | Что показывать                                                          |
| ----- | ------------------------------------- | ----------------------------------------------------------------------- |
| `200` | Успех                                 |                                                                         |
| `201` | Комментарий создан                    |                                                                         |
| `204` | Удалено (авария, комментарий)         |                                                                         |
| `400` | Невалидное тело или query-параметры   | Ошибки полей, см. ниже                                                  |
| `401` | Нет/просрочен токен                   | Разлогин, редирект на вход                                              |
| `403` | Нет права                             | Прячьте кнопку заранее (2.6); если всё же пришло — тост с `detail` |
| `404` | Нет объекта **или** он чужого тенанта | «Авария не найдена»                                                     |

Ошибки DRF приходят либо как `{"detail": "..."}`, либо как объект по полям:

```json
{ "ids": ["Ensure this field has no more than 500 elements."] }
```

Ошибки правил вложены по структуре JSON правила — разбор в
[4.8](#48-как-показывать-ошибки-валидации).

### 2.6. Права и видимость элементов

На сервере проверяются **Django-права**. В токене их нет, поэтому фронт забирает их из своего
пользователя — `user_id` берётся из полезной нагрузки access-токена:

```http
GET /api/v1/users/user/<user_id>/
```

В ответе — `roles[]`, у каждой роли `permissions[]` (объекты с `codename`) и
`additional_info.ui_permissions` (строковые UI-ключи проекта).

Для аварий есть и то, и другое:

| Действие в UI                                                    | Django-право (`codename`)                                   | UI-ключ                             |
| ---------------------------------------------------------------- | ----------------------------------------------------------- | ----------------------------------- |
| Видеть раздел «Аварии», таблицу, карточку, комментарии, счётчики | `view_alarm`                                                | `s-gen-alarms`, `s-gen-alarms-read` |
| Кнопка «Квитировать», массовое квитирование                      | `ack_alarm`                                                 | `s-gen-alarms-edit`                 |
| Кнопка «Закрыть», массовое закрытие                              | `clear_alarm`                                               | `s-gen-alarms-edit`                 |
| Кнопка «Назначить»                                               | `assign_alarm`                                              | `s-gen-alarms-edit`                 |
| Кнопка «Удалить аварию»                                          | `delete_alarm`                                              | `s-gen-alarms-edit`                 |
| Поле ввода комментария, правка и удаление своего                 | `change_alarm`                                              | `s-gen-alarms-edit`                 |
| Открыть конструктор правил, превью                               | `view_alarmrule`                                            | права профилей устройств            |
| Создать правило                                                  | `add_alarmrule`                                             | права профилей устройств            |
| Изменить правило, массовая замена                                | `change_alarmrule`                                          | права профилей устройств            |
| Удалить правило                                                  | `delete_alarmrule`                                          | права профилей устройств            |
| Каталог ключей (`available-keys`)                                | `view_deviceprofile`                                        | права профилей устройств            |
| Экран «Уведомления»                                              | `view_notificationsettings` / `change_notificationsettings` | настройки тенанта                   |

Важные нюансы:

- **`s-gen-alarms*` сервер не проверяет** — это только для скрытия элементов. Решение о доступе
  принимают Django-права, поэтому прятать кнопку по UI-ключу, но слать запрос без права —
  гарантированный `403`.
- У роли `TENANT_ADMIN` все права на аварии выданы фикстурой; суперпользователь имеет все права и
  видит аварии **всех** тенантов в списке, карточке и счётчиках.
- Комментарий можно править и удалять **только свой** и только пользовательский: у `SYSTEM`-записей
  кнопок быть не должно (сервер ответит `403`).

## 3. Экраны аварий

Таблица, живые обновления, карточка и плашки на дашборде — четыре части одного
рабочего места дежурного.

### 3.1. Таблица и фильтры

Активные аварии и журнал — **один и тот же эндпоинт**, разница только в фильтре `status`. Делайте
один экран с переключателем, а не два.

```http
GET /api/v1/alarms/?status=ACTIVE&severity=CRITICAL&severity=MAJOR&page=1&size=25
```

#### Фильтры

| Параметр               | Тип             | Примечание                                                                                                             |
| ---------------------- | --------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `status`               | строка          | `ACTIVE`, `CLEARED`, `UNACK`, `ACK`, `ACTIVE_UNACK`, `ACTIVE_ACK`, `CLEARED_UNACK`, `CLEARED_ACK`. Без параметра — все |
| `alarm_type`           | повторяемый     | Значения берите из `GET alarms/types/`                                                                                 |
| `severity`             | повторяемый     | `CRITICAL`, `MAJOR`, `MINOR`, `WARNING`, `INDETERMINATE`                                                               |
| `device`               | UUID            | Аварии устройства **и** аварии, распространённые на него (авария шлюза)                                                |
| `room`                 | UUID            | Номер, в котором стояло устройство на момент создания аварии                                                           |
| `assignee`             | UUID или `none` | `none` — неназначенные. Пустая строка не фильтрует                                                                     |
| `date_from`, `date_to` | ISO 8601        | По `start_ts`, границы включительно                                                                                    |
| `search_value`         | строка          | Подстрока в типе аварии, имени устройства или номере комнаты                                                           |
| `sort_by`              | повторяемый     | `start_ts`, `end_ts`, `severity`, `alarm_type`, с `-` для убывания. По умолчанию `-start_ts`                           |
| `page`, `size`         | числа           |                                                                                                                        |

Статусы `ACTIVE`/`CLEARED` смотрят только на `cleared`, `UNACK`/`ACK` — только на `acknowledged`,
составные — на оба флага. Поэтому «активные неквитированные» — это `ACTIVE_UNACK`, а не два
параметра.

#### Ответ

```json
{
  "count": 1,
  "results": [
    {
      "id": "0b3e6a52-4d7e-4f0e-9a51-2d5b8a0f3c11",
      "alarm_type": "Gateway Offline",
      "severity": "CRITICAL",
      "status": "ACTIVE_UNACK",
      "acknowledged": false,
      "cleared": false,
      "start_ts": "2026-09-14T10:18:00.412305Z",
      "end_ts": "2026-09-14T10:41:30.108214Z",
      "ack_ts": null,
      "clear_ts": null,
      "duration_ms": 1409695,
      "details": {
        "message": "Шлюз GW-3 не на связи",
        "values": { "active": false, "is_gateway": true }
      },
      "tenant": "28c81921-f78e-4864-87d2-cec674f19d1c",
      "originator": "5e6f7a8b-9c0d-4e1f-a2b3-c4d5e6f7a8b9",
      "originator_name": "GW-3",
      "room": null,
      "room_number": null,
      "assignee": null,
      "assign_ts": null,
      "propagate_entity_ids": ["1b2c3d4e-5f60-4718-8293-a4b5c6d7e8f9"],
      "notified_at": null,
      "created_at": 1789381080412
    }
  ]
}
```

#### Что выводить в колонках

| Колонка      | Поле              | Как                                                    |
| ------------ | ----------------- | ------------------------------------------------------ |
| Время        | `start_ts`        | Для активных дополнительно «длится N» из `duration_ms` |
| Severity     | `severity`        | Цвет и иконка, таблица ниже                            |
| Тип          | `alarm_type`      |                                                        |
| Сообщение    | `details.message` | Может быть `null` — тогда покажите `alarm_type`        |
| Устройство   | `originator_name` | Ссылка по `originator`                                 |
| Номер        | `room_number`     | Может быть `null` (устройство без номера)              |
| Статус       | `status`          | Четыре значения, см. ниже                              |
| Исполнитель  | `assignee`        | Объект `{id, email}` или `null`                        |
| Длительность | `duration_ms`     | Для закрытых — итог, для активных — «пока что»         |

`duration_ms` считает сервер: для закрытых это `clear_ts − start_ts`, для активных —
`end_ts − start_ts`. Для активной аварии `end_ts` — время последнего прохода вычислителя, на
котором условие ещё выполнялось, то есть «длительность» подросла до последней проверки, а не до
«сейчас». Если нужен живой счётчик — считайте от `start_ts` до текущего времени сами.

Severity и статусы:

| Severity        | Вес | Предлагаемый цвет | Иконка в Telegram |
| --------------- | --- | ----------------- | ----------------- |
| `CRITICAL`      | 1   | красный           | 🔴                |
| `MAJOR`         | 2   | оранжевый         | 🟠                |
| `MINOR`         | 3   | жёлтый            | 🟡                |
| `WARNING`       | 4   | синий             | 🔵                |
| `INDETERMINATE` | 5   | серый             | ⚪                |

| `status`        | Смысл                               | Подсказка в UI                  |
| --------------- | ----------------------------------- | ------------------------------- |
| `ACTIVE_UNACK`  | Активна, никто не отреагировал      | Выделять, это главное состояние |
| `ACTIVE_ACK`    | Активна, но квитирована             | «В работе»                      |
| `CLEARED_UNACK` | Закончилась, но никто не квитировал | Бывает: авария закрылась сама   |
| `CLEARED_ACK`   | Закончилась и квитирована           | Обычная строка журнала          |

#### Сортировка по severity — только на клиенте

`sort_by=severity` сортирует **по алфавиту**: `CRITICAL`, `INDETERMINATE`, `MAJOR`, `MINOR`,
`WARNING`. Это не порядок важности. Если нужна сортировка по важности — забирайте страницу и
сортируйте по весу из таблицы выше:

```ts
const WEIGHT = {
  CRITICAL: 1,
  MAJOR: 2,
  MINOR: 3,
  WARNING: 4,
  INDETERMINATE: 5,
} as const;
rows.sort((a, b) => WEIGHT[a.severity] - WEIGHT[b.severity]);
```

Либо вообще не предлагайте сортировку по этой колонке, а дайте фильтр по severity — он работает
на сервере и не ломается на пагинации.

#### Справочник типов для фильтра

```http
GET /api/v1/alarms/types/
```

```json
{ "results": ["Device Offline", "Gateway Offline", "High Temperature"] }
```

Это типы, которые **уже встречались** у тенанта, а не типы из правил профилей. На свежей
инсталляции список пустой — фильтр по типу в этом случае лучше скрыть или оставить свободный ввод.
Типы содержат пробелы, в query-строку их нужно кодировать (`URLSearchParams` сделает сам).

#### Пустые состояния

| Ситуация                       | Что показать                                                                                                                                 |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `count: 0` при `status=ACTIVE` | «Активных аварий нет» — это хорошая новость, не ошибка                                                                                       |
| `count: 0` с фильтрами         | «Ничего не найдено» + кнопка сброса фильтров                                                                                                 |
| `types/` пусто и журнал пуст   | «Аварий ещё не было». Если у тенанта нет правил, добавьте подсказку со ссылкой на конструктор правил — без правил аварии не появятся никогда |

### 3.2. Живые обновления (WebSocket)

Таблицу аварий не нужно опрашивать по таймеру: есть стрим `alarms` в общем v2-демультиплексоре.

#### Подключение

```ts
const socket = new WebSocket(
  `wss://${apiHost}/api/ws/v2/?token=${accessToken}`,
);
```

Токен передаётся **в query-строке**, заголовки в браузерном WebSocket недоступны. Неверный или
просроченный токен — сервер закрывает соединение с кодом **4001**: это сигнал обновить токен и
переподключиться, а не повторять подключение в цикле.

#### Подписка

Каждое сообщение адресуется стриму:

```json
{
  "stream": "alarms",
  "payload": {
    "action": "list_subscribe",
    "request_id": 42,
    "query_params": {
      "status": "ACTIVE_UNACK",
      "severity": ["CRITICAL", "MAJOR"],
      "page": 1,
      "size": 50
    }
  }
}
```

- `request_id` — ваш произвольный идентификатор, он вернётся в каждом ответе по этой подписке;
- `query_params` — те же фильтры, что в REST, но **списки передаются массивами**
  (`"severity": ["MAJOR"]`, строка вызовет ошибку валидации);
- если `status` не передан, стрим отдаёт **только активные** — для журнала задавайте его явно;
- `action: "list"` — то же самое, но разово, без подписки;
- `action: "list_unsubscribe"` с тем же `request_id` — отписка.

#### Ответ

```jsonc
{
  "stream": "alarms",
  "payload": {
    "errors": [],
    "data": { "count": 3, "results": [/* те же объекты аварий */] },
    "action": "list_subscribe",
    "response_status": 200,
    "request_id": 42
  }
}
```

Приходит сразу после подписки и затем при каждом изменении — сервер присылает **всю страницу**
заново, с вашими фильтрами и `request_id`. Отдельных событий «авария создана/изменена» нет:
заменяйте весь список целиком.

Ошибка в `query_params` придёт так же, но с `response_status: 400` и заполненным `errors`.

#### Когда обновление приходит, а когда нет

| Приходит                                                                         | Не приходит                                      |
| -------------------------------------------------------------------------------- | ------------------------------------------------ |
| Авария создана                                                                   | Сдвиг `end_ts` на очередном проходе вычислителя  |
| Severity эскалирована                                                            | Обновление `details.message` без смены состояния |
| Авария снята (сама или вручную)                                                  | Новый комментарий                                |
| `ack`, `clear`, `assign`, удаление, массовые действия — чьи угодно, включая ваши |                                                  |

Отсюда два следствия: «длительность» в таблице не тикает сама (3.1), а комментарии в
открытой карточке нужно перезапрашивать после своих действий.

#### Одна подписка на соединение

`list_unsubscribe` выводит соединение из группы тенанта целиком — обновления перестанут приходить
**всем** подпискам `alarms` этого сокета. Поэтому:

- держите одну подписку `alarms` на соединение;
- при смене фильтров делайте `list_unsubscribe` → `list_subscribe` с новыми `query_params`;
- не подписывайтесь второй раз на тот же стрим из другого компонента — выносите подписку в стор.

#### Каркас клиента

```ts
type AlarmPage = { count: number; results: Alarm[] };

const REQUEST_ID = 1;

export function subscribeAlarms(
  socket: WebSocket,
  filters: AlarmFilters,
  onPage: (page: AlarmPage) => void,
) {
  const send = (action: string, extra: object = {}) =>
    socket.send(
      JSON.stringify({
        stream: "alarms",
        payload: { action, request_id: REQUEST_ID, ...extra },
      }),
    );

  socket.addEventListener("message", (event) => {
    const frame = JSON.parse(event.data);
    if (frame.stream !== "alarms" || frame.payload?.request_id !== REQUEST_ID)
      return;

    if (frame.payload.response_status >= 400) {
      console.error("alarms stream error", frame.payload.errors);
      return;
    }
    onPage(frame.payload.data);
  });

  send("list_subscribe", { query_params: filters });
  return () => send("list_unsubscribe");
}
```

При реконнекте подписку нужно оформить заново — сервер ничего не помнит о прошлом соединении.
Страницу на время разрыва лучше один раз дотянуть через REST, чтобы не показывать устаревшие данные.

#### UUID во WebSocket приходят без дефисов

Особенность всех v2-стримов: внешние ключи `tenant`, `originator`, `room` сериализуются как
32 hex-символа **без дефисов** (`"28c81921f78e486487d2cec674f19d1c"`), тогда как `id`,
`assignee.id` и `propagate_entity_ids` — в обычном виде с дефисами. В REST все UUID с дефисами.

Если сравниваете id (например, «это авария открытого устройства?») — нормализуйте:

```ts
const sameId = (a: string, b: string) =>
  a.replace(/-/g, "") === b.replace(/-/g, "");
```

### 3.3. Карточка и действия

```http
GET /api/v1/alarms/<id>/
```

Возвращает тот же объект, что в списке. Чужая авария или неверный id — `404`.

#### Действия

| Кнопка           | Запрос                     | Тело                        | Что меняется                                                                           |
| ---------------- | -------------------------- | --------------------------- | -------------------------------------------------------------------------------------- |
| Квитировать      | `POST alarms/<id>/ack/`    | —                           | `acknowledged: true`, `ack_ts`, `SYSTEM`-комментарий. Повторный вызов ничего не делает |
| Закрыть          | `POST alarms/<id>/clear/`  | —                           | `cleared: true`, `clear_ts`, `SYSTEM`-комментарий «Cleared manually»                   |
| Назначить        | `POST alarms/<id>/assign/` | `{"assignee": "<user_id>"}` | `assignee`, `assign_ts`                                                                |
| Снять назначение | `POST alarms/<id>/assign/` | `{"assignee": null}`        | `assignee: null`, `assign_ts: null`                                                    |
| Удалить          | `DELETE alarms/<id>/`      | —                           | `204`, авария и её комментарии исчезают навсегда                                       |

Все, кроме удаления, возвращают обновлённый объект аварии — обновляйте карточку из ответа.

Нюансы для UI:

- **Закрывать вручную стоит только после устранения причины.** Если условие правила всё ещё
  выполняется, вычислитель создаст новую аварию в течение ближайших ~30 секунд. То же с удалением.
  Разумно показывать подтверждение с этим предупреждением.
- **Исполнитель** должен быть активным пользователем того же тенанта, иначе `404`. Список для
  выпадающего меню берите из `GET /api/v1/users/users/`.
- **Удаление** стирает инцидент из журнала. Для истории правильнее «Закрыть».
- Квитирование и закрытие — независимые оси: закрытую аварию можно квитировать, и наоборот.

#### Комментарии

```http

```

Массив **без пагинации**, новые сверху:

```json
[
  {
    "id": "3c4d5e6f-7a8b-4c9d-8e0f-1a2b3c4d5e6f",
    "alarm_comment_type": "OTHER",

      "email": "engineer@hotel.uz"
    },
    "created_at": 1789381332000
  },
  {
    "id": "8f9a0b1c-2d3e-4f5a-9b6c-7d8e9f0a1b2c",
    "alarm_comment_type": "SYSTEM",

      "email": "engineer@hotel.uz"
    },
    "created_at": 1789381212551
  }

```

Создать — `POST alarms/<id>/comments/` с `{"text": "..."}` (до 4000 символов), ответ `201`.
Править — `PUT alarms/<id>/comments/<comment_id>/` с тем же телом, удалять — `DELETE`, `204`.

**Два типа записей рендерятся по-разному.** `OTHER` — реплика человека. `SYSTEM` — системная
запись о событии жизненного цикла; её нельзя править и удалять (сервер ответит `403`), и показывать
её лучше как событие в таймлайне, а не как сообщение:

| `comment.subtype`  | Дополнительные поля | Что показать                                                                    |
| ------------------ | ------------------- | ------------------------------------------------------------------------------- |
| `SEVERITY_CHANGED` | `from`, `to`        | «Severity повышена: MINOR → MAJOR»                                              |
| `ACKNOWLEDGED`     | —                   | «Квитировано, <email>»                                                          |
| `CLEARED`          | —                   | «Закрыто» (текст `Alarm cleared` — автоматически, `Cleared manually` — вручную) |
| `ASSIGNED`         | `assignee`          | «Назначено на <email>»                                                          |
| `UNASSIGNED`       | `assignee: null`    | «Назначение снято»                                                              |

У `SYSTEM`-записей вычислителя `user` равен `null` — это сделал сервер, а не человек.

У своего `OTHER`-комментария после правки в `comment` появляются `edited: true` и `edited_at` —
удобно подписать «изменено».

Ошибки правки:

| Ответ                                                    | Причина                          |
| -------------------------------------------------------- | -------------------------------- |
| `403 {"detail": "System comments are read-only."}`       | Пытаетесь править `SYSTEM`       |
| `403 {"detail": "You can only edit your own comments."}` | Комментарий другого пользователя |

## 4. Конструктор правил

У правил свой CRUD: правило — отдельная сущность с FK на профиль устройства, действует на все
активные устройства этого профиля. Условия внутри правила описаны в формате ThingsBoard, поля в
**camelCase** — в отличие от конверта (`device_profile`, `enabled`) и остального API, где
snake_case.

Семантика (что такое `DURATION`, как считается расписание, в каком порядке перебираются severity)
— в [`alarms.md` §4–5](alarms.md#4-формат-правил). Здесь — что показывать в форме.

### 4.1. Где лежат правила

У каждого правила своя строка и свой адрес — профиль пересохранять не нужно.

```http
GET /api/v1/alarms/rules/?device_profile=<profile_id>
```

```json
{
  "count": 1,
  "results": [
    {
      "id": "4f1c9a0b-62d7-4f1e-9b3a-5c8d7e6f0a12",
      "device_profile": "7c1e2a8e-3b0f-4a8e-9f0d-51b7e0c7a4d2",
      "device_profile_name": "Thermostats",
      "enabled": true,
      "alarmType": "High Temperature",
      "createRules": {"MINOR": {"condition": {"condition": [], "spec": {"type": "SIMPLE"}}}},
      "clearRule": null,
      "propagate": false,
      "propagateRelationTypes": [],
      "propagateToOwner": false,
      "propagateToTenant": false,
      "created_at": 1789381080412,
      "updated_at": 1789381080412
    }
  ]
}
```

Тело правила — это объект ThingsBoard (camelCase) плюс конверт GRMS (snake_case):
`device_profile`, `enabled`, и в ответах `id`, `device_profile_name`, `created_at`, `updated_at`.
Смешение регистров умышленное: так рецепт из документации или экспорт из TB вставляется в тело
без переделки.

Фильтры списка: `device_profile`, `alarm_type` (повторяемый), `enabled`, `search_value`,
`sort_by` (`alarm_type`, `created_at`, с `-`), `page`, `size` (по умолчанию 50).

У нового тенанта правил нет вообще — список пустой, пока пользователь их не создаст. Профили для
выбора: `GET /api/v1/main/device-profile/`.

### 4.2. Создание, изменение, удаление

```http
POST /api/v1/alarms/rules/            → 201, созданное правило
PUT  /api/v1/alarms/rules/<id>/       → 200, изменённое правило
DELETE /api/v1/alarms/rules/<id>/     → 204
```

Что важно для формы:

1. **`PUT` частичный.** Отправляйте только изменённое. Выключить правило — `{"enabled": false}`,
   пересылать условия не нужно.
2. **`device_profile` обязателен при создании** и задаёт тенанта правила: поле `tenant` в теле
   не принимается.
3. **`alarmType` уникален внутри профиля.** Второе правило того же типа на том же профиле — `400`
   с ошибкой в `alarmType`. На другом профиле тот же тип допустим.
4. **Ответ нормализован.** Сервер дописывает значения по умолчанию (`spec: {"type": "SIMPLE"}`,
   `ignoreCase: false`, `inherit: false`, `timezone: "UTC"`, `propagate*: false`), поэтому
   перечитывайте форму из ответа — иначе следующее сохранение уйдёт с «вашей» версией правила.
5. **Удаление не трогает журнал.** Аварии, поднятые этим правилом, остаются; но их больше никто
   не снимет автоматически, поэтому предложите закрыть их через `bulk/clear/`.

```ts
const created = await api.post("alarms/rules/", { device_profile: profileId, ...rule });
await api.put(`alarms/rules/${created.id}/`, { enabled: false });
await api.delete(`alarms/rules/${created.id}/`);
```

**Сохранить весь редактор разом** — `POST /api/v1/alarms/rules/bulk/`:

```json
{"device_profile": "7c1e2a8e-3b0f-4a8e-9f0d-51b7e0c7a4d2", "alarms": [{"alarmType": "Device Offline", "createRules": {}}]}
```

Сопоставление по `alarmType`: правило из массива обновляет существующее того же типа (id и
история сохраняются), новые типы создаются, **отсутствующие в массиве удаляются**. Пустой массив
очищает все правила профиля. Ответ `200` — итоговый список правил профиля.

Это же путь импорта: массив `alarms` имеет точно тот формат, который экспортирует профиль
ThingsBoard.

Изменения подхватываются вычислителем на следующем проходе — до 30 секунд, никаких
дополнительных действий не нужно.

### 4.3. Каталог ключей

Поле ключа в условии — не свободный ввод: опечатка даёт правило, которое никогда не сработает,
и никакой ошибки при этом не будет. Поэтому ключи выбираются из каталога:

```http
GET /api/v1/alarms/available-keys/?search_value=temp
```

```json
{
  "timeseries": ["AC Setpoint", "Room Temperature"],
  "attributes": [
    "active",
    "gatewayActive",
    "lastActivityTime",
    "notifyOnOffline"
  ],
  "entity_fields": [
    "name",
    "type",
    "label",
    "status",
    "is_active",
    "is_gateway",
    "room.number",
    "room.floor",
    "room.state"
  ]
}
```

- `timeseries` — ключи телеметрии, которые реально присылали устройства тенанта → `key.type: "TIME_SERIES"`;
- `attributes` — серверные атрибуты устройств → `key.type: "ATTRIBUTE"`;
- `entity_fields` — фиксированный белый список полей устройства и его номера → `key.type: "ENTITY_FIELD"`;
- `search_value` фильтрует первые два списка (подстрока, без учёта регистра);
- ответ **кешируется на 5 минут**: ключ, появившийся только что, в каталоге будет с задержкой.
  Стоит разрешить ручной ввод как резерв, но с предупреждением.

### 4.4. Структура правила и поля формы

Одно правило (`DeviceProfileAlarm`) — одна «карточка» в редакторе:

| Поле JSON                                                                      | Контрол                                                                      | Обязательность   |
| ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- | ---------------- |
| `alarmType` | Текст, до 255 символов. Уникален внутри профиля | да |
| `id` | Только чтение: UUID правила. В теле запроса игнорируется | — |
| `createRules`                                                                  | Объект `severity → правило`. В UI — вкладки или список блоков по severity    | да, минимум один |
| `clearRule`                                                                    | Такой же блок, но без `alarmDetails`                                         | нет              |
| `propagate`, `propagateRelationTypes`, `propagateToOwner`, `propagateToTenant` | Чекбоксы + список типов связей | нет |
| `device_profile` | Селектор профиля | да при создании |
| `enabled` | Переключатель «правило включено» | нет, по умолчанию `true` |

Блок одной severity (`AlarmRule`):

| Поле JSON             | Контрол                                                             |
| --------------------- | ------------------------------------------------------------------- |
| `condition.condition` | Список фильтров (AND между ними), минимум один                      |
| `condition.spec`      | Селектор «сработать сразу / держится N времени / N проверок подряд» |
| `schedule`            | Селектор «всегда / окно / по дням»                                  |
| `alarmDetails`        | Текст шаблона сообщения с подстановками                             |
| `dashboardId`         | Не используется, не показывайте                                     |

Дерево целиком:

```text
правило (alarmType)
├── createRules
│   └── CRITICAL | MAJOR | MINOR | WARNING | INDETERMINATE
│       ├── condition
│       │   ├── condition[]        ← фильтры, объединяются через AND
│       │   │   ├── key {type, key}
│       │   │   ├── valueType
│       │   │   ├── value          ← только для key.type = CONSTANT
│       │   │   └── predicate      ← NUMERIC | BOOLEAN | STRING | COMPLEX
│       │   └── spec               ← SIMPLE | DURATION | REPEATING
│       ├── schedule               ← ANY_TIME | SPECIFIC_TIME | CUSTOM
│       └── alarmDetails
├── clearRule                      ← та же структура
└── propagate*
```

### 4.5. Редактор фильтра

Фильтр — «значение ключа» + «условие на него»:

```json
{
  "key": { "type": "TIME_SERIES", "key": "Room Temperature" },
  "valueType": "NUMERIC",
  "predicate": {
    "type": "NUMERIC",
    "operation": "GREATER",
    "value": { "defaultValue": 30 }
  }
}
```

**Шаг 1 — ключ.** Селектор источника (`TIME_SERIES`, `ATTRIBUTE`, `ENTITY_FIELD`, `CONSTANT`) и
селектор имени из каталога. Для `CONSTANT` имя не нужно, но обязательно поле `value` с литералом.

**Шаг 2 — тип значения (`valueType`).** Определяет и то, как сервер прочитает значение, и то,
какой предикат допустим. Жёсткая связка, её проверяет валидатор:

| `valueType` | Разрешённый `predicate.type` | Когда выбирать                                   |
| ----------- | ---------------------------- | ------------------------------------------------ |
| `NUMERIC`   | `NUMERIC`                    | Числа: температура, уставка, влажность           |
| `BOOLEAN`   | `BOOLEAN`                    | Флаги: `active`, `notifyOnOffline`, `is_gateway` |
| `STRING`    | `STRING`                     | Текст: имя, номер комнаты, версия прошивки       |
| `DATE_TIME` | `NUMERIC`                    | Метки времени (Unix-мс), сравниваются как числа  |

Подсказка для формы: при смене `valueType` сбрасывайте `predicate` целиком — операции у типов
разные.

**Шаг 3 — предикат.** Операции по типам:

| Тип       | Операции                                                                                     | Дополнительно                                                                               |
| --------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `NUMERIC` | `EQUAL`, `NOT_EQUAL`, `GREATER`, `LESS`, `GREATER_OR_EQUAL`, `LESS_OR_EQUAL`                 |                                                                                             |
| `BOOLEAN` | `EQUAL`, `NOT_EQUAL`                                                                         | Значение — переключатель `true`/`false`                                                     |
| `STRING`  | `EQUAL`, `NOT_EQUAL`, `STARTS_WITH`, `ENDS_WITH`, `CONTAINS`, `NOT_CONTAINS`, `IN`, `NOT_IN` | Чекбокс `ignoreCase`; для `IN`/`NOT_IN` — список значений (массив или строка через запятую) |
| `COMPLEX` | `AND`, `OR` над вложенными предикатами                                                       | Глубина вложенности **не больше 5**                                                         |

`COMPLEX` — это «несколько условий на **один и тот же** ключ»: диапазон, набор исключений.
Условия на разные ключи — это разные фильтры в списке (они и так объединяются через AND). OR
между разными ключами в этом формате невыразим — нужны два отдельных правила.

```json
{
  "type": "COMPLEX",
  "operation": "OR",
  "predicates": [
    { "type": "NUMERIC", "operation": "LESS", "value": { "defaultValue": 30 } },
    {
      "type": "NUMERIC",
      "operation": "GREATER",
      "value": { "defaultValue": 70 }
    }
  ]
}
```

**Шаг 4 — значение порога.** Это не просто число, а объект:

```json
{
  "defaultValue": 30,
  "dynamicValue": {
    "sourceType": "CURRENT_ROOM",
    "sourceAttribute": "temperatureMax",
    "inherit": true
  }
}
```

| Поле           | Контрол                                                                                            |
| -------------- | -------------------------------------------------------------------------------------------------- |
| `defaultValue` | Значение по типу: число / переключатель / текст / список                                           |
| `dynamicValue` | Необязательный блок «брать из атрибута»: селектор источника + имя атрибута + чекбокс «искать выше» |

Источники: `CURRENT_DEVICE` (серверный атрибут устройства), `CURRENT_ROOM`
(`additional_info.attributes` номера), `CURRENT_TENANT` (то же у тенанта). `inherit: true` —
если атрибута нет, искать выше по цепочке `устройство → номер → тенант`; не нашлось нигде —
берётся `defaultValue`.

Нужно хотя бы одно из двух: и `defaultValue`, и `dynamicValue` пустые — `400`. В UI это
формулируется как «Порог» + необязательная галочка «Переопределять на номере/тенанте».

### 4.6. Редактор спецификации

| `spec.type` | Поля                                                                   | Текст для UI                          |
| ----------- | ---------------------------------------------------------------------- | ------------------------------------- |
| `SIMPLE`    | —                                                                      | «Сработать сразу»                     |
| `DURATION`  | `unit`: `SECONDS`/`MINUTES`/`HOURS`/`DAYS`, `predicate` — значение > 0 | «Условие держится непрерывно N минут» |
| `REPEATING` | `predicate` — целое ≥ 1                                                | «Условие выполнено N проверок подряд» |

```jsonc
{"type": "DURATION", "unit": "MINUTES", "predicate": {"defaultValue": 10}}
{"type": "REPEATING", "predicate": {"defaultValue": 3}}
```

`predicate` здесь — такой же объект значения, как у порога, поэтому длительность тоже можно брать
из атрибута. В простой форме достаточно `defaultValue`.

Что важно объяснить пользователю прямо в форме:

- проверки идут раз в ~30 секунд, поэтому `REPEATING 3` ≈ «минута подряд», а не «три сообщения
  от устройства»;
- одна неудачная проверка сбрасывает и таймер `DURATION`, и счётчик `REPEATING` — условие должно
  держаться **непрерывно**;
- у `clearRule` спецификация тоже работает: «снимать только если N минут всё хорошо».

### 4.7. Редактор расписания

| `schedule.type` | Поля                                                            |
| --------------- | --------------------------------------------------------------- |
| `ANY_TIME`      | — (эквивалент отсутствия `schedule`)                            |
| `SPECIFIC_TIME` | `timezone`, `daysOfWeek: number[]`, `startsOn`, `endsOn`        |
| `CUSTOM`        | `timezone`, `items[]`: `{enabled, dayOfWeek, startsOn, endsOn}` |

```json
{
  "type": "SPECIFIC_TIME",
  "timezone": "Asia/Tashkent",
  "daysOfWeek": [1, 2, 3, 4, 5],
  "startsOn": 32400000,
  "endsOn": 64800000
}
```

Правила, которые легко забыть:

- дни недели — **ISO**: понедельник `1` … воскресенье `7`;
- `startsOn`/`endsOn` — **миллисекунды от полуночи** в указанной таймзоне, диапазон `0…86400000`;
- `timezone` — IANA-имя (`Asia/Tashkent`); неизвестное значение → `400`. По умолчанию `UTC`,
  но лучше подставлять зону отеля явно;
- `startsOn == endsOn` — весь день;
- `startsOn > endsOn` — окно через полночь (`23:00 → 07:00`). День недели проверяется по
  **текущему** дню, поэтому для «каждую ночь» перечисляйте все семь дней;
- в `CUSTOM` день, которого нет в `items`, или с `enabled: false` — правило не действует весь день.

Конвертация времени:

```ts
const toMs = (hours: number, minutes = 0) => (hours * 60 + minutes) * 60_000;
const fromMs = (ms: number) => ({
  hours: Math.floor(ms / 3_600_000),
  minutes: (ms % 3_600_000) / 60_000,
});
// 09:00 → 32400000, 18:00 → 64800000, 23:00 → 82800000, 24:00 → 86400000
```

Предупреждение для UI: вне расписания правило не просто «молчит», оно теряет накопленный отсчёт
`DURATION`. Окно 09:00–18:00 с длительностью 15 минут не сработает на инциденте, начавшемся в 08:55.

### 4.8. Как показывать ошибки валидации

Сервер возвращает `400`, повторяя **структуру JSON правила**, так что ошибку можно подсветить
прямо в нужном поле формы. Для одного правила (`POST`/`PUT`) путь начинается сразу с поля:

```json
{
  "createRules": {
    "MAJOR": {
      "condition": {
        "condition": [
          {},
          {
            "predicate": [
              "valueType NUMERIC needs NUMERIC predicates, got ['BOOLEAN']."
            ]
          }
        ],
        "spec": {
          "predicate": ["A DURATION needs a positive 'defaultValue'."]
        }
      }
    }
  }
}
```

Читается так: блок `MAJOR`, фильтр с индексом `1`, поле `predicate`. Пустой объект `{}` —
валидный элемент массива, индексы сохраняются.

В `rules/bulk/` и `rules/preview/` то же самое завёрнуто в `alarms` с индексом правила:

```json
{"alarms": [{}, {"createRules": ["This dictionary may not be empty."]}]}
```

Частые сообщения:

| Текст                                                          | Что не так                                |
| -------------------------------------------------------------- | ----------------------------------------- |
| `valueType NUMERIC needs NUMERIC predicates, got ['BOOLEAN'].` | `valueType` и `predicate.type` не совпали |
| `A DURATION needs a positive 'defaultValue'.`                  | Длительность `0` или отрицательная        |
| `A REPEATING count must be an integer of at least 1.`          | Дробное или нулевое число повторов        |
| `Either 'defaultValue' or 'dynamicValue' is required.`         | Пустой порог                              |
| `This dictionary may not be empty.`                            | `createRules` без ни одной severity       |
| `Duplicate alarmType: ['High Temperature'].`                   | Два правила с одним типом в профиле       |
| `ENTITY_FIELD must be one of [...]`                            | Поле вне белого списка                    |
| `A CONSTANT key needs a 'value'.`                              | У `CONSTANT` не задан литерал             |
| `Nested COMPLEX predicates may not go deeper than 5.`          | Слишком глубокая вложенность              |
| `Unknown timezone 'Asia/Tashkent2'.`                           | Опечатка в таймзоне                       |
| `A COMPLEX predicate needs at least one child.`                | Пустой `predicates`                       |

### 4.9. Превью — обязательный шаг перед сохранением

Кривое правило открывает аварию на каждом устройстве профиля и рассылает их в Telegram. Поэтому
перед сохранением прогоняйте правила по текущим данным:

```http
POST /api/v1/alarms/rules/preview/
Content-Type: application/json

{"device_profile": "<profile_id>", "alarms": [/* правила из формы, ещё не сохранённые */]}
```

Без `alarms` прогоняются **включённые** правила профиля, то есть «что сработает сейчас».

```jsonc
{
  "device_count": 42,
  "alarms": [
    {
      "alarmType": "High Temperature",
      "create_rules": [
        {
          "severity": "MINOR",
          "spec": "DURATION",
          "matched_count": 2,
          "sample": [
            {
              "id": "9a4d7c2e-1f3b-4c5d-8e6f-7a8b9c0d1e2f",
              "name": "Thermostat 305",
              "room": "305",
              "message": "Температура 27.6° в номере 305"
            },
            {
              "id": "1b2c3d4e-5f60-4718-8293-a4b5c6d7e8f9",
              "name": "Thermostat 412",
              "room": "412",
              "message": "Температура 28.1° в номере 412"
            }
          ]
        }
      ],
      "clear_rule": { "matched_count": 38, "sample": [/* ... */] }
    }
  ]
}
```

Как это показывать:

- `matched_count` из `device_count` — «условию сейчас соответствует 2 из 42 устройств»;
- `sample` — до пяти примеров с уже отрендеренным сообщением: пользователь видит, как будет
  выглядеть авария;
- `matched_count` близко к `device_count` — **красный флаг**: почти наверняка перепутаны операция
  или масштаб порога. Стоит показать предупреждение и спросить подтверждение;
- `spec` и `schedule` при превью **игнорируются** — оно отвечает на вопрос «выполняется ли условие
  сейчас», а не «сработает ли через 10 минут». Подпишите это, иначе `matched_count: 2` при
  `DURATION` будет выглядеть как «сейчас появятся 2 аварии»;
- `clear_rule` — `null`, если правила снятия нет;
- невалидные правила получают `400` с той же структурой ошибок (4.8) — превью заодно работает
  кнопкой «Проверить».

Ничего в базу превью не пишет.

### 4.10. Шаблон сообщения `alarmDetails`

Строка с подстановками `${...}`, результат попадает в `details.message` аварии и в Telegram.
Доступны:

| Подстановка                        | Значение                                                                                          |
| ---------------------------------- | ------------------------------------------------------------------------------------------------- |
| `${originatorName}`                | Имя устройства                                                                                    |
| `${room}`                          | Номер комнаты или пустая строка                                                                   |
| `${alarmType}`, `${alarmSeverity}` | Тип и severity                                                                                    |
| `${<ключ>}`                        | Значение ключа телеметрии, атрибута или поля: `${Room Temperature}`, `${active}`, `${room.floor}` |

Пробелы в именах ключей допустимы. Нераспознанная подстановка останется в тексте как есть —
это не ошибка, но выглядит плохо, поэтому в редакторе давайте вставку из каталога ключей, а не
ручной ввод.

Гарантированно подставляются только ключи, которые **используются в условиях** этого правила
или других правил профиля. Пустой шаблон даёт `"<alarmType> — <имя устройства>"`.

### 4.11. Распространение

| Поле                     | Чекбокс в UI                                    | Что делает                                                                                  |
| ------------------------ | ----------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `propagate`              | «Показывать на связанных устройствах»           | Авария видна в карточках устройств, связанных с источником (например, устройства за шлюзом) |
| `propagateRelationTypes` | Список типов связей, по умолчанию пусто = любые | Сужает связи                                                                                |
| `propagateToOwner`       | «Привязать к номеру»                            | Добавляет id номера                                                                         |
| `propagateToTenant`      | «Привязать к тенанту»                           | Добавляет id тенанта                                                                        |

Результат виден в `propagate_entity_ids` аварии и в фильтре `?device=<id>`, который отдаёт в том
числе распространённые аварии. Вычисляется **один раз при создании** аварии: связи, добавленные
позже, старую аварию не расширят.

### 4.12. Клиентская валидация перед отправкой

Чтобы не ловить `400`, проверьте в форме:

- `alarmType` непустой и уникален среди правил профиля;
- хотя бы одна severity в `createRules`;
- в каждом условии хотя бы один фильтр;
- `predicate.type` соответствует `valueType` (таблица в 4.5), в том числе у всех вложенных в `COMPLEX`;
- у значения есть `defaultValue` либо `dynamicValue` с непустым `sourceAttribute`;
- `DURATION`: `unit` выбран, значение > 0; `REPEATING`: целое ≥ 1;
- у `CONSTANT`-ключа заполнен `value`, у остальных — `key.key`;
- расписание: дни выбраны, время в диапазоне `0…86400000`, таймзона из списка IANA;
- глубина `COMPLEX` ≤ 5;
- `COMPLEX` не пустой.

### 4.13. Шаблоны: откуда взять готовое правило

Пустой конструктор — плохая отправная точка: собрать работающее правило связи с нуля, не читая
документацию, почти невозможно. Поэтому есть каталог готовых правил.

```http
GET /api/v1/alarms/rule-templates/
```

```json
{
  "results": [
    {
      "id": "high-temperature",
      "name": "Высокая температура",
      "description": "Температура выше 30° дольше 5 минут. Порог можно переопределить на номере атрибутом «temperatureMax».",
      "requires": {"attributes": [], "timeseries": ["Room Temperature"]},
      "rule": {"alarmType": "High Temperature", "createRules": {"MINOR": {}}, "clearRule": {}}
    }
  ]
}
```

Сейчас их четыре: `device-offline`, `gateway-offline`, `high-temperature`, `low-temperature`.
Первые два — пара правил связи с нужными фильтрами, которую иначе пришлось бы собирать руками.

**Сценарий в UI**

1. Кнопка «Добавить типовое правило» → список из `results` (`name` + `description`);
2. выбор → `rule` подставляется в форму конструктора как есть;
3. пользователь правит порог или длительность;
4. обычный `POST /api/v1/alarms/rules/` с добавленным `device_profile`.

Поле `requires` — ключи, на которых держится шаблон. Фронт уже тянет
[`available-keys`](#43-каталог-ключей): сравните списки и помечайте шаблон как неприменимый, если
тенант не присылает нужную телеметрию. Правило на ключ, которого нет, молча никогда не сработает —
это самый неприятный способ «сломать» мониторинг.

```ts
function isApplicable(template: AlarmRuleTemplate, keys: AvailableKeys): boolean {
  return (
    template.requires.timeseries.every((key) => keys.timeseries.includes(key)) &&
    template.requires.attributes.every((key) => keys.attributes.includes(key))
  );
}
```

Шаблоны ничего не создают сами: пока пользователь не выберет шаблон и не сохранит правило, у
тенанта правил нет. Полный разбор каждого шаблона и ещё десяток рецептов под конкретные задачи —
в [`alarms.md` §6](alarms.md#6-правила-связи-устройства-и-шлюзы) и
[§7](alarms.md#7-рецепты).

## 5. Настройки уведомлений и тумблер устройства

Два небольших экрана, без которых аварии некуда отправлять.

### 5.1. Настройки уведомлений тенанта

Экран «Настройки → Уведомления». Ресурс одиночный, без id — всегда настройки текущего тенанта.

```http
GET /api/v1/main/notification-settings/
```

```json
{
  "tenant_id": "28c81921-f78e-4864-87d2-cec674f19d1c",
  "telegram_enabled": true,
  "telegram_chat_id": "-1002345678901",
  "telegram_last_error": null,
  "notify_delay_sec": 300,
  "min_severity": "MINOR"
}
```

`PUT` — **частичный**, можно отправить только изменённые поля:

```http
PUT /api/v1/main/notification-settings/
Content-Type: application/json

{"telegram_enabled": true, "telegram_chat_id": "-1002345678901", "min_severity": "MAJOR"}
```

| Поле                  | Контрол               | Диапазон  | Подпись для пользователя                                                               |
| --------------------- | --------------------- | --------- | -------------------------------------------------------------------------------------- |
| `telegram_enabled`    | Переключатель         |           | «Присылать аварии в Telegram»                                                          |
| `telegram_chat_id`    | Текст, до 64 символов |           | «Id чата или группы». У групп отрицательный, у супергрупп начинается с `-100`          |
| `notify_delay_sec`    | Число                 | `0…86400` | «Не сообщать об авариях, которые закрылись быстрее, чем за N секунд». По умолчанию 300 |
| `min_severity`        | Селектор severity     |           | «Сообщать об этой важности и выше»                                                     |
| `telegram_last_error` | Только чтение         |           | Текст последней постоянной ошибки Telegram                                             |

Как это показывать:

- `telegram_last_error` непустой — выведите предупреждение рядом с полем чата: «Telegram отклонил
  отправку: `<текст>`». Типичные причины — бот не добавлен в группу, бот удалён из неё, неверный
  id чата. Поле сбрасывается в `null` при любом сохранении `telegram_chat_id`, так что после
  исправления предупреждение исчезнет само.
- Задержка объясняется проще всего так: авария появится в журнале сразу, а в Telegram — через
  `notify_delay_sec`; если она закроется раньше, сообщения не будет вовсе.
- Токен бота задаётся на сервере в переменных окружения и через API не виден. Если он не задан,
  уведомления не уйдут, и внешне это выглядит как «включено, но ничего не приходит» —
  инструкция по настройке бота для админа есть в [`alarms.md` §10.1](alarms.md#101-настройка).

### 5.2. Тумблер на карточке устройства

В сериализаторе устройства есть булево поле `notify_on_offline` — это обёртка над серверным
атрибутом `notifyOnOffline`, на который опирается правило «устройство не на связи».

```http
GET /api/v1/main/device/<device_id>/     →  {"...": "...", "notify_on_offline": true}
```

Записывается в обычном теле устройства:

```http
PUT /api/v1/main/device/<device_id>/
Content-Type: application/json

{"...": "все поля устройства из GET", "notify_on_offline": false}
```

- `PUT` устройства тоже **полный** — отправляйте объект, полученный из `GET`, с изменённым полем.
- Поле необязательное: не передали — атрибут не меняется.
- У устройств, созданных до появления тумблера, атрибута может не быть; API в этом случае
  возвращает `true`.
- При создании устройства значение по умолчанию — `true`.

Подпись должна честно объяснять эффект: **выключенный тумблер отключает не только уведомления, но
и сами аварии** этого устройства по правилу связи — в журнале их тоже не будет. На пользовательские
правила тумблер влияет только если они сами фильтруют по `notifyOnOffline`.

В списке устройств поле тоже приходит, отдельного запроса на каждое устройство не нужно.

## 7. Грабли и чеклист приёмки

Короткая выжимка: на чём проще всего ошибиться и что проверить перед сдачей.

### 7.1. Грабли

| Что                                                                             | Почему важно                                                                   |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `PUT` устройства — **полный**, не частичный | Отправляйте объект из `GET` с изменённым полем. У правил (`alarms/rules/<id>/`) `PUT`, наоборот, частичный |
| `rules/bulk/` **удаляет** правила, которых нет в массиве | Одно правило меняйте через `POST`/`PUT`/`DELETE`; `bulk` — только когда отправляете весь набор |
| `sort_by=severity` сортирует по алфавиту                                        | Сортировку по важности делайте на клиенте (3.1)                                |
| В WebSocket `tenant`, `originator`, `room` — UUID **без дефисов**               | Сравнивайте id нормализованными (3.2)                                          |
| `list_unsubscribe` отключает все подписки стрима на этом сокете                 | Держите одну подписку на соединение (3.2)                                      |
| WS молчит при сдвиге `end_ts` и при новых комментариях                          | «Длительность» не тикает сама; комментарии перезапрашивайте (3.2)              |
| `created_at` — число (Unix-мс), остальные даты — строки ISO                     | Не передавайте в `new Date()` одинаково не глядя                               |
| `+` в датах фильтра нужно кодировать как `%2B`                                  | Используйте `URLSearchParams`, не склеивайте строки                            |
| Чужая авария даёт `404`, а не `403`                                             | Сообщение «не найдена», а не «нет доступа»                                     |
| `available-keys` кешируется на 5 минут                                          | Только что появившийся ключ в каталоге не виден сразу                          |
| `alarms/types/` отдаёт только **встречавшиеся** типы                            | На свежей инсталляции список пустой                                            |
| `assignee=none` — это фильтр «неназначенные», а не отсутствие фильтра           | Пустую строку не отправляйте                                                   |
| `alarmType` уникален внутри профиля (на разных профилях повторяться может) | Второе правило того же типа — `400` в поле `alarmType` |
| Выключенное правило (`enabled: false`) не создаёт и **не снимает** аварии | Активные аварии после выключения закрываются только вручную |
| `preview` игнорирует `spec` и `schedule` | Подпишите: «условие выполняется сейчас», а не «авария появится» |
| Ручное закрытие или удаление при выполненном условии → новая авария через ~30 с | Предупреждайте в диалоге подтверждения                                         |
| `bulk/*` принимает максимум 500 id, `updated` может быть меньше `requested`     | Показывайте фактический результат                                              |
| Severity эскалируется только вверх                                              | «Понижения» не бывает — не рисуйте его в истории                               |
| `notify_on_offline: false` отключает и аварии, и уведомления устройства         | Подпись должна это объяснять                                                   |
| У нового тенанта правил нет вообще                                              | Пока правила не созданы, аварий не будет — добавьте подсказку на пустом экране |
| `ack` идемпотентен, `assign` пишет `SYSTEM`-запись при каждом вызове            | Не дёргайте `assign` на каждый ввод в поиске по пользователям                  |
| `details.message` может быть `null`                                             | Фолбэк на `alarm_type`                                                         |
| `room_number` может быть `null`                                                 | Устройство бывает без номера                                                   |

### 7.2. Чеклист приёмки

**Таблица аварий**

- [ ] переключатель «Активные / Журнал» меняет `status`, а не эндпоинт;
- [ ] фильтры по типу, severity, номеру, устройству, исполнителю, периоду и поиску уходят на сервер;
- [ ] пагинация считается от `count`;
- [ ] сортировка по severity не выглядит сломанной (на клиенте или отсутствует);
- [ ] подписка на WS одна, переподключение после `4001` обновляет токен;
- [ ] пустые состояния различают «нет аварий» и «ничего не найдено».

**Карточка**

- [ ] `ack` / `clear` / `assign` обновляют карточку из ответа;
- [ ] кнопки скрыты без соответствующего права;
- [ ] `SYSTEM`-комментарии показаны как события и без кнопок правки;
- [ ] у чужого и системного комментария нет кнопок, свой — правится и удаляется;
- [ ] закрытие и удаление спрашивают подтверждение и предупреждают о повторном появлении.

**Конструктор правил**

- [ ] есть кнопка «Добавить типовое правило» из `rule-templates/`, неприменимые шаблоны помечены по `requires`;
- [ ] ключи выбираются из `available-keys`, свободный ввод помечен как рискованный;
- [ ] `valueType` жёстко связан с типом предиката, при смене предикат сбрасывается;
- [ ] пороги поддерживают `dynamicValue` с выбором источника и `inherit`;
- [ ] время в расписании вводится как часы:минуты, а в API уходит в миллисекундах от полуночи;
- [ ] дни недели — ISO, понедельник первый;
- [ ] перед сохранением вызывается `preview`, результат показан человеку;
- [ ] ошибки `400` подсвечиваются в полях формы по пути из ответа;
- [ ] одно правило сохраняется через `POST`/`PUT` правила, а не массовой заменой;
- [ ] форма перечитывается из ответа `PUT`.

**Настройки и устройство**

- [ ] `telegram_last_error` показан как предупреждение;
- [ ] `notify_delay_sec` объяснён словами, а не только числом;
- [ ] тумблер `notify_on_offline` сохраняется полным телом устройства.
